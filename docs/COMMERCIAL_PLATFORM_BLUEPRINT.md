# 叙界商业化与平台升级蓝图

更新时间：2026-08-24

## 结论与边界

现有项目已经拥有稀缺而正确的基础：确定性叙事引擎、Content Pack/Release 不可变版本、RLS、多租户、BYOK、SSE、管理员 MFA、审计日志、异步任务和基础可观测性。下一步不应推倒重来，而是围绕它补齐商业产品的四个闭环：**玩家体验、权益计量、内容运营、生产运维**。

本次首期实现已经加入 `wallet_ledger`、`payment_orders` 与 `credit_campaigns`：余额由不可变账本汇总，管理员修正与运营赠点必须经过 MFA、CSRF、理由、幂等键与审计记录。支付渠道尚未启用；在签约、地区、税务和回调验签方案确认前，系统不会伪装成可以收款。

## 目标架构

```text
Next.js 玩家端 / 创作台 / 管理运营台
                 │ HTTPS + HttpOnly session + CSRF
FastAPI API ─────┼──── 身份、权限、目录、游戏、商业、审核
                 │
                 ├── PostgreSQL：RLS、Release、游戏状态、钱包账本、订单快照、审计
                 ├── Redis：限流、锁、队列、幂等与短时缓存
                 ├── Worker：邮件、审核、导出、支付回调、账单、通知、数据聚合
                 ├── S3：素材、导出与版本化备份
                 └── OTel / Prometheus / Sentry：指标、追踪、告警与错误聚合

LLM Provider / BYOK
       │
Usage Ledger → 使用事件 → 权益检查/预授权 → 钱包结算 → 运营指标
```

原则：游戏引擎仍是世界状态的唯一裁决者；钱包账本仍是商业权益的唯一裁决者；支付商只提供“是否支付成功”的外部证据，不能直接改写余额。

## 商业领域模型与收费规则

### 账户与权益

| 概念 | 唯一真相 | 规则 |
| --- | --- | --- |
| 月度免费额度 | `users.platform_quota_monthly` + `usage_ledger` | 用于产品试用和管理员配额，不等于现金余额。 |
| 叙点余额 | `wallet_ledger.credit_delta` 的累加 | 不在用户表保存可被覆盖的“余额”列；每次变化新增一条记录。 |
| 订单 | `payment_orders` 的价格快照 | 保留当时套餐、币种、金额、渠道和有效期，不能被后来改价篡改。 |
| 运营赠点 | `credit_campaigns` + `wallet_ledger` | 活动限定状态、有效期和可选领取上限；成功领取创建一笔不可变账目。 |
| 订阅与其他权益 | Plan/Entitlement（下一期） | 会员、创作者能力和其他未来权益分别建模，不与现金余额混写。 |
| LLM 用量 | `usage_ledger` | 记录 provider、model、token、成本和成功状态，不混入支付事实。 |

### 推荐收费模型

1. 免费层：每月有限平台托管额度，保证新用户能完成首次故事体验。
2. 叙点包：预付费，按已公开的“模型成本 → 叙点”规则结算；适合高频玩家。
3. 会员层：每月赠点、较高并发、长篇叙事、优先模型队列、更多存档与创作能力。
4. BYOK：不收推理费用，只提供平台功能；必须清晰标识由玩家承担模型服务商费用。
5. 创作者未来收入：作品销售、订阅或打赏与平台叙点**分账**。在 KYC、税务、退款和版权合同完成前，不向创作者承诺可提现余额。

### 结算不变量

- 平台模型在回合前做最高成本预授权；回合后按真实可核验成本结算，多退少补。
- 生成失败、确定性降级、被安全策略拒绝的调用不收叙点。
- 退款、拒付、人工修正只能写反向账目；禁止更新或删除原账目。
- 每个订单、支付回调、赠送活动、回合结算都必须有全局可追溯的幂等键。
- 任何扣减不得让可用余额小于零；争议金额使用 `hold`/预授权，不把负数当成普通状态。
- 所有金额用最小货币单位整数；叙点用整数；禁止浮点数。
- 活动赠点只能在 `active` 且有效期内领取，先锁定活动行、检查上限和玩家专属幂等键，再新增账目并递增领取数；重复请求必须返回同一领取结果，绝不重复到账。

## 支付通道上线门槛

支付渠道取决于经营主体和售卖地区，不能由代码猜测。确认以下内容后再接入相应适配器：

1. 主体、服务地区、币种、是否需要发票/税务处理。
2. 首发渠道：支付宝/微信支付、Stripe、App Store/Google Play，或其他本地支付商。
3. 退款时限、拒付证据、未成年消费和风控策略。
4. webhook 的签名验证、事件去重、重放保护、死信队列与人工对账流程。
5. 隐私政策、用户协议、内容分级、客服与争议工单路径。

支付适配器必须做到：浏览器只创建 Checkout Session；服务端验证已签名 webhook；Worker 以订单行锁处理一次事件；最后新增钱包账目和审计日志。绝不能以“前端跳转成功”或“客户端回传成功”作为到账依据。

## 玩家体验升级路线

### 首屏与发现

- 已实现首屏“免费开始/继续故事”和“浏览作品”双主按钮，并提供公开价格入口；后续补充编辑精选、题材与时长预览。
- 作品库支持题材、时长、情绪、玩法机制、分级、语言、创作者和“适合新手”筛选；使用编辑精选与个性化推荐分栏。
- 试玩在第一回合前告知存档、模型模式、预计消耗与内容提示。

### 游戏过程

- 保持当前沉浸式叙事布局，增加“本回合进度/预计消耗/降级说明”的非侵入状态条。
- 把记忆、关系、任务、时钟和存档统一为可回退的侧栏；移动端只显示当前最相关的两个模块。
- 每个失败状态都给出可行动恢复路径：重试、改用 BYOK、减少篇幅、查看服务状态、联系客服。
- 结局页提供回顾、成就、同世界新开局、分享卡和反馈；不强迫分享。

### 账户与信任

- 已增加“余额中心”，明确区分平台托管模型和 BYOK，并展示逐笔记录。
- 登录恢复：已实现邮箱重置、同一时间仅一条有效重置链接、设备会话撤销、账户内安全改密、TOTP/恢复码、恢复码轮换与用户自助安全事件时间线；已登录玩家可通过支持工单获得协助。失去注册邮箱的人工找回仍须先确定身份核验与客服流程，不能仅凭工单放行。
- 已增加“帮助与支持”入口：玩家可提交账户、余额、故事异常等工单并在自己的线程中补充信息；系统不自动附带故事正文、密钥、IP 或支付凭据。账号删除会清除工单正文，个人数据导出会包含其工单与消息。
- 已增加玩家专属“通知中心”：支持团队回复、运营活动权益到账会作为可已读的内部链接通知出现，不把故事正文、密钥、支付凭据或管理员内部备注带入通知。通知受 RLS 保护，纳入个人数据导出，并随账号删除清除。
- 删除账户时保留满足法定留存所需的去标识化财务审计记录；游戏与个人数据按既有延迟注销机制清除。

## 管理运营台

管理员拥有业务上的最高操作权限，但不应拥有无痕改写历史的能力。

| 能力 | 规则 |
| --- | --- |
| 用户、角色、会话、额度 | 已有；写操作需 MFA、CSRF、理由和审计。查看玩家账户总览、具体故事正文或工单对话同样是 POST + MFA/CSRF + 理由 + 独立审计，玩家可自助查看访问记录。 |
| 余额修正 | 已实现；幂等、不可透支、追加账目、审计。大额修正下一期改为双人审批。 |
| 商业总览 | 已实现聚合指标：有余额账户、发放/结算/在途叙点、账目数、30 天净变动、订单状态和按状态的活动数。 |
| 风险信号 | 已实现从持久账本、模型用量、支持队列和安全审计实时计算的关键告警：高模型失败率、过期预授权、未分派紧急/超时工单、异常登录聚集。信号只返回聚合数量和处理锚点，不返回玩家身份或内容，也不能被点击“已读”掩盖。 |
| 套餐与价格 | 已实现；后台可审核并发布停用/启用套餐，玩家与访客可看见公开价格，但不会创建订单或扣款。 |
| 支付配置 | 待经营决策；密钥仅部署环境注入，加密存储配置摘要，不回显明文。 |
| 内容审核与紧急下架 | 已有；保留申诉、证据和操作日志。 |
| 客服与异常恢复 | 已实现玩家专属工单、附加回复、管理员队列、优先级/分派/状态流转和审计；后台总览显示待处理与未分派数量。多渠道收件箱和经身份核验的失去邮箱找回留待客服系统接入。 |
| 运营活动 | 已实现面向全体已验证用户的赠点活动：后台创建/启用/暂停/结束，必须有有效期、可选上限和操作理由；玩家仅看到可领取活动，每人一次、账本幂等、全程审计。指定受众、预算审批、批量发放和回滚工作流留待下一期。 |
| 超级权限 | 已实现独立 `super_admin` 权限集、部署环境的首次引导、24 小时双人审批请求、请求人不可自批、受保护的授予/撤销、保留至少一名超级管理员、MFA/CSRF 与审计。IP/设备审计留待下一期。 |

## 指标、SLO 与告警

现有 HTTP 指标、结构化日志、Sentry、traceparent 和 LLM 成本告警应扩展为下面三类仪表盘：

| 仪表盘 | 关键指标 | 初始告警建议 |
| --- | --- | --- |
| 玩家体验 | 注册→首局→首回合→第三回合→结局漏斗、D1/D7 留存、SSE 首字与完整回合延迟、错误率 | 5xx > 1%、P95 回合完成 > 45s、SSE 断流异常增加。 |
| LLM/FinOps | 模型调用数、token、成本、降级率、按模型/作品/用户层级的预算消耗 | 日成本预测超过预算 80%、失败率 > 3%、单用户异常消耗。 |
| 商业与风控 | 活动展示→领取→到账、充值创建→支付成功→入账转化、退款/拒付率、账本不平衡、人工调账 | 活动上限接近耗尽、webhook 未处理、账目/订单不匹配、人工调账异常、负余额尝试。 |

指标标签不得使用邮箱、玩家输入、完整故事文本、支付凭证或 API 密钥。对玩家级排查使用受审计的单用户查看，不把 PII 放入 Prometheus 标签。

## 外部开源调研与采用建议

- [OpenMeter](https://github.com/openmeterio/openmeter)（Apache-2.0）是 AI/API 用量、预付费额度、权益和订阅的成熟参考。适合第二阶段评估接入；它依赖 Kafka/ClickHouse 等，当前不应为了早期流量过早引入其完整拓扑。
- [OpenTelemetry Python Contrib](https://github.com/open-telemetry/opentelemetry-python-contrib) 提供 FastAPI、SQLAlchemy 等自动埋点。适合把现有 `traceparent`/指标升级成标准 trace，而不是自造链路系统。
- [Stripe Python SDK](https://github.com/stripe/stripe-python) 仅在经营主体和地区选择 Stripe 后使用。支付商 SDK 只能负责 API 与验签，订单/余额的业务真相仍保留在本项目。
- [Nellavio](https://github.com/nellavio/nellavio)（MIT）可作为数据密集型 Next.js 管理台的信息架构和组件组合参考；不应整仓搬运，当前 API、会话与 RLS 边界应保持不变。
- [Fugue](https://github.com/GetfroggyHoe/Universal-Immersion-Engine-Fugue) 与 [RPGForge](https://github.com/want7up1/Rpgforge) 的可取之处是“AI 写作、确定性状态与持久世界分层”。本项目已经具备更强的 Release/RLS 边界，可参考其玩家体验，不复制其架构。
- [Langfuse](https://github.com/langfuse/langfuse)（MIT，部分企业功能除外）值得作为下一阶段的 LLM trace、提示词版本、评测与数据集平台；先保持本项目的最小化指标与审计，待部署团队确认私有化存储、采样、保留期和访问边界后再接入。
- [Chatwoot](https://github.com/chatwoot/chatwoot) 是可自托管的多渠道客服参考。当前原生工单提供最小必要的玩家隔离和管理员审计；如果要接入邮件、网站聊天或社媒入口，应通过脱敏的适配器同步，不把密码、密钥、完整故事和支付凭据推送到第三方收件箱。

以上只用于设计和验证方向；引入任何代码、素材或模型前必须逐项检查许可证、商标、隐私和供应商条款。

## 分期实施

1. **P0（已完成首轮）**：钱包账本、订单快照、余额中心、商业概览、管理调账、回合预授权与真实结算、迁移和回归测试。
2. **P1（进行中）**：公开价格套餐、首屏与定价体验、可审计活动赠点、通知中心；支付商适配器、验签 webhook、支付/退款对账须在经营决策完成后接入。
3. **P2**：KYC 与创作者结算、发票/税务、反欺诈评分、合规留存策略。
4. **P3**：OpenTelemetry Collector、Grafana/Tempo、产品事件仓库、A/B 实验、推荐与内容运营工作流。
5. **P4**：移动端 PWA/原生支付、社交与关注、多人世界（需独立的并发和安全设计）。

## 下一次需要确认的业务决策

在接入实际扣款前，需要产品负责人确认：首发国家/地区、收款主体、首发支付渠道、币种与税务、定价与赠点有效期、是否售卖订阅、退款和未成年人政策。代码已经为这些选择预留了安全边界，但不会擅自替代经营与法律决策。
